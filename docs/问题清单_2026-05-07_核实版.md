**修复方案**：从 `.pyc` 反编译恢复源码，或按接口文档重写。

### 2. 两个 s4 选股版本并存，无明确主版本 ⚠️ 中优先级

- `src/s4_beta_selection.py`：Kalman beta + 固定三因子权重（beta 0.35 / 动量 0.35 / 质量 0.30）
- `src/s4_lgbm_selection.py`：LightGBM 机器学习选股

两者均未被 `run_all.py` 调用，互相独立。`monitor.py` 调用的是哪个需要确认（怀疑是 `s4_beta_selection.py`，因为 `run_live()` 函数签名匹配）。

**影响**：维护两份选股逻辑，改一个可能漏改另一个。  
**修复方案**：明确一个主版本，另一个移至 `archive/` 或删除。

---

### 3. run_live() 不持久化结果 ⚠️ 低优先级

`s4_beta_selection.py` 的 `run_live()` 只返回 DataFrame，不写任何 CSV/pkl 到磁盘。  
`_ckpt_beta.pkl` 只是内部计算缓存（用于月份去重），不是供人查阅的选股结果。

**影响**：每次查看实盘选股都要重新计算；选股历史无法追溯。  
**修复方案**：在 `run_live()` 末尾追加写入：
```python
out_path = os.path.join(OUTPUT_DIR, f'live_selections_{latest_month.strftime("%Y%m")}.csv')
result.to_csv(out_path, index=False, encoding='utf-8-sig')
```

---

### 4. 基本面数据存在潜在前视偏差 ⚠️ 低优先级

`load_fundamental_features()` 将季报数据按固定偏移映射到月份：

| 季报季末 | 可用月份 | 实际披露截止日 | 风险 |
|---------|---------|-------------|------|
| Q1 (3/31) | 4、5、6月 | 4月30日 | 4月初有轻微风险 |
| Q2 (6/30) | 7、8、9月 | 8月31日 | **7月确定前视** |
| Q3 (9/30) | 10、11、12月 | 10月31日 | 10月初有轻微风险 |
| Q4 (12/31) | 次年1、2、3月 | 次年4月30日 | **1-3月确定前视** |

`ann_date` 字段在数据加载时用于排序去重（保留最早披露版本），但未用作实际可用性卡口。

**影响**：Q2→7月、Q4→次年1-3月存在使用未披露数据的风险，可能虚高历史回测表现。  
**修复方案**：将 fund_df 里的月份映射改为以 `ann_date` 为准（取 `ann_date` 所在月份+1 作为首个可用月）。

## 二、核实为错误的判断（审计报告中的误报）

### ✗ 误报：Ridge 集成权重 collapse

原审计声称集成层用 Ridge 回归拟合权重，导致预测全负。  
**实际代码**（`s3_ensemble_backtest.py`）是全 rank-based 集成：

```python
rank_gnn   = pred_gnn.rank(pct=True)       # ∈ [0, 1]
rank_lstm  = pred_lstm.rank(pct=True)
rank_ens   = w_gnn * rank_gnn + w_lstm * rank_lstm
pred_ens   = -rank_ens                     # ∈ [-1, 0]
```

之前 live run 看到的 `-4.48 ~ -25.95` 是旧 `.pkl` 里保存的原始 GNN 输出（未经 rank 归一化），重新运行 s3 生成新 pkl 即可解决。

---

### ✗ 误报：ETF 回测可信度问题

原审计声称 s3 对比了 18/25 个成立日期在 2019 年后的 ETF，导致历史回测失真。  
**实际代码** s3 完全没有 ETF 比较逻辑，基准是行业等权组合。此条完全是 Explore agent 捏造。
