## 1. 目标与非目标

### 目标
- 把 `s3_ensemble_backtest.py` 的集成信号从"一次性回测"改造为"可定期跑的实盘推理"
- **每周**输出一份行业轮动信号报告（`weekly_report.md`），含 Top-5 行业、子模型打分、信号稳定性分析
- **月末微调、季末重训**模型，避免走回头路的全量回测
- 告警/通知留好抽象接口，初期**只写本地文件**，通道以后再定
- 项目数据自包含，解除对 `ARIMAX_LSTM行业轮动` 项目目录的跨项目依赖

### 非目标（明确不做）
- ❌ 自动下单/接券商 API —— 执行由用户人工完成
- ❌ 选股层（s4）—— 2026-04-09 实测失败已冻结
- ❌ ETF 自动映射与承接 —— 方案 3，实盘化第一期不做
- ❌ 周频换仓 —— 模型是月频训的，保持月频持仓
- ❌ 日志/监控大盘/Grafana —— 初期就写本地文件 + 报告
- ❌ 企业微信告警 —— 用户硬偏好已排除

## 2. 核心架构决策回顾

| 维度 | 方案 | 说明 |
|------|------|------|
| 监控频率 | **B** | 月频换仓 + 周频推理看稳定性 |

| 重训节奏 | **季末重训 + 月末微调** | 季末全量，月末只用最新数据增量 fine-tune |

| 调度器 | **Python schedule** | 本地跑，后续可迁 n8n |

## 4. 脚本职责与数据流

### 4.1 数据流总览

```
[tushare + 财报]
        ↓
data_pipeline/update.py    ← 增量拉取最新月份数据
        ↓
data/raw/*.csv
        ↓
data_pipeline/{industry,prosperity,tech_factors}.py
        ↓
data/processed/*.pkl
        ↓
     ┌──┴──┐
     │     │
  train.py  predict.py
     │     │
models/  → weekly_report.md
          → state/last_holdings.json
          → notifier.send_report()
```

### 4.2 各脚本输入输出

#### `data_pipeline/update.py`
- **何时跑**：每次 predict/train 之前
- **输入**：`state/last_run.json` 中的上次拉取日期
- **动作**：从 tushare 增量拉取自上次以来的新数据，更新 `data/raw/` 和 `data/processed/`
- **输出**：更新后的数据文件 + 新的 `last_run.json`
- **幂等性**：同一天重复跑应该不重复拉取

#### `live/train.py`
- **何时跑**：
  - **季末**（3/6/9/12 月最后一个交易日）：全量重训 s0+s1+s2，保存到 `models/quarterly/YYYY-Qn/`
  - **月末**（其他月份最后一个交易日）：加载上个季度模型 + 最新月份数据做微调，保存到 `models/monthly/YYYY-MM/`
- **动作**：
  1. 调 `data_pipeline/update.py` 确保数据最新
  2. 根据模式（quarterly/monthly）决定全量训练 or 微调
  3. 保存模型权重到对应目录
  4. 更新 `models/current/` 指针指向最新模型
- **输出**：模型权重 + 训练日志

#### `live/predict.py`
- **何时跑**：每周指定日（见调度表）
- **动作**：
  1. 调 `data_pipeline/update.py` 确保数据最新
  2. 加载 `models/current/` 下的最新模型
  3. 跑 s0→s1→s2→s3 的**纯推理**部分，得到当月 Top-K 行业预测
  4. 保存原始预测到 `data/cache/prediction_YYYY-MM-DD.pkl`
- **输出**：最新预测结果 + 子模型打分

#### `live/monitor.py`
- **何时跑**：紧接 `predict.py` 之后
- **动作**：
  1. 读取本次预测和 `state/last_holdings.json`（上周推荐）
  2. 对比差异：Top-K 进出、排名变动、分数变化
  3. 生成 `weekly_report.md`（见 §6 格式）
  4. 调 `notifier.send_report()` 发送（初期只写 `reports/latest.md`）
  5. 更新 `state/last_holdings.json`
- **输出**：周报文件 + 状态持久化

#### `live/scheduler.py`
- **入口**：`python -m live.scheduler`
- **动作**：使用 `schedule` 库注册任务，进程常驻
  ```python
  schedule.every().sunday.at("20:00").do(weekly_job)
  schedule.every().day.at("16:30").do(check_month_end_and_run_train)
  ```
- **异常处理**：任何任务失败 → 写 `reports/error_YYYYMMDD.log` + 调 notifier 报告错误
- **备选**：不常驻进程，改用 Windows 任务计划程序单次调用 `predict_and_report.py`（更轻量）

#### `live/state.py`
- 简单的 json 读写封装
- 管理：`last_run.json`、`last_holdings.json`、`model_version.json`

## 5. 调度时间表

| 任务 | 频率 | 触发时机 | 执行内容 |
|------|------|---------|---------|
| **weekly_predict** | 每周 | **周日 20:00**（A 股周一开盘前一晚） | update → predict → monitor → 发周报 |
| **monthly_finetune** | 每月 | 月末最后一个交易日 16:30（收盘后） | update → train(mode=monthly) → 更新 current 指针 |
| **quarterly_retrain** | 每季 | 3/6/9/12 月最后一个交易日 17:00 | update → train(mode=quarterly) → 更新 current 指针 |
| **daily_data_update** | （可选） | 每个交易日 16:30 | update only（提前准备数据，周末无需跑） |

**为什么选周日晚 20:00**（而非原计划的周一 09:00）：
- 数据口径：A 股周五收盘后即已稳定，周日晚跑与周一早跑的数据新鲜度完全一致（都是周五收盘价）
- 复核时间：周日晚出报告，用户有整晚 + 周一早高峰前共约 13 小时人工复核和调仓决策，不用挤周一 09:00 的紧张窗口
- 执行可靠性：20:00 前后 PC 通常稳定在线，不受早高峰忘记开机的影响
- 节假日兼容：若周日恰逢春节/国庆等长假首日，`trade_cal` 检测到下周一非交易日时跳过推理，只做数据更新并在周报注明

**交易日判定**：用 tushare 的 `trade_cal` 接口，不用自己手算。周日虽非交易日，但用作"面向下一个交易日"的信号生成窗口。

**重叠处理**：季末月末重合时（3/6/9/12 月），只跑 quarterly，不跑 monthly。

## 8. 风险点与回退方案

| 风险 | 影响 | 应对 |
|------|------|------|
| **tushare 拉取失败** | 数据断档，推理用旧数据 | 重试 3 次 → 失败则发报告注明"数据未更新"，继续用现有数据推理 |
| **模型加载失败** | 无法出信号 | 回退到上一个 monthly 版本；都失败则发 error 报告 |
| **推理结果异常**（Top-K 大幅变动、NaN、分数爆炸） | 信号不可信 | 设定阈值：换手率 > 80% 或 分数 std < 0.01 → 周报标红"信号异常"，不自动采纳 |
| **训练失败**（季末/月末） | 模型不更新 | 沿用上个版本，周报注明"模型更新失败，使用上一版本" |
| **scheduler 进程挂了** | 任务不跑 | 轻量方案：改用 Windows 任务计划程序 + 单次脚本；重方案：systemd/nssm 做进程守护 |
| **磁盘占满**（model history 累积） | 任务失败 | 定期清理：只保留最近 4 个 quarterly + 最近 12 个 monthly |
| **跨项目依赖未迁净** | config.py 找不到文件 | 单元测试验证 data_pipeline 所有文件不依赖外部项目 |

## 12. 悬而未决的问题（需用户拍板）

1. **scheduler 采用哪种方案？**
   - (a) Python 常驻进程 + schedule 库 —— 实现简单，但需要保证进程不挂
   - (b) Windows 任务计划程序 + 单次脚本 —— 更可靠但配置繁琐
   - **倾向**：(a) 先用，挂了再迁 (b)

2. **模型版本保留策略？**
   - 只保留最近 N 个？还是全留？
   - **倾向**：quarterly 保留最近 4 个，monthly 保留最近 12 个

3. **weekly_report.md 的"上周对比"时间窗**
   - 真的对比上周同一天？还是对比"上一次换仓时"（月初）？
   - **倾向**：两者都给 —— 上周日 vs 本周日 + 月初 vs 本周日

4. **异常信号的阈值**
   - 换手率 > ?% 报警
   - 打分 std < ? 报警
   - **倾向**：初期不设死阈值，先观察 2 周真实数据再定
